# Runtime protocol v1

The desktop shell and the background runtime use the same Rust executable. `AgentCouncil.exe --serve` starts the headless runtime. Closing a window does not stop accepted work. A single runtime owns subprocesses and SQLite state; multiple UI connections do not start duplicate jobs.

The workspace also builds a GUI-independent `CouncilHost` executable using the same host library. Revision **9** supports Claude and Codex account profiles. Login preparation remains replay-safe. Local companion management routes live under `/v1/companion`. Build commands, native data paths and remaining macOS gaps are documented in [PORTABLE_HOST.md](PORTABLE_HOST.md).

The runtime binds an ephemeral **127.0.0.1** port, writes its address and a random bearer credential under the user's AgentCouncil data directory, and requires that credential on every API request. The desktop bootstrap command reads these locally. Nothing is exposed to a LAN or tailnet automatically. The source companion preview adds a separate opt-in gateway with device pairing/revocation; its [contract](COMPANION_API.md) is distinct from this administrator API. Native mobile packaging and automatic Tailscale configuration are not enabled.

All requests and events are JSON. Routes begin `/v1`. HTTP errors return `{ "error": "message" }`. Unknown or missing credentials return 401. Mutation requests are size limited. Configuration rejects unknown agents and nonexistent project/reference folders. Only one job per project runs at a time (409 for duplicates). Accepted jobs receive an ID before execution; network disconnects do not cancel them.

| Method/path | Purpose |
|---|---|
| GET /v1/state | Settings, detected CLIs, current project's messages, job, token totals, account limits, durable event cursor |
| PUT /v1/settings | Save coder (nullable), reviewers, folder, references, language, appearance and permissions |
| PUT /v1/draft | Save `{folder,text}` independently of agent work |
| POST /v1/files/read | Read `{target}` from the selected project or references; supports local file links and line suffixes, returns `{path,name,text,line,start_line,truncated}` |
| POST /v1/jobs | Start `{request,request_id}`; repeat request_id returns the same accepted job |
| GET /v1/jobs/{id}/changes | Desktop-only, no-store response with the completed job's bounded file comparison |
| POST /v1/jobs/{id}/cancel | Cancel a running job including its CLI process trees |
| GET /v1/events?after=N | SSE event replay followed by live events; persisted monotonic IDs permit reconnect |
| POST /v1/usage/refresh | Read available local account limits; unavailable providers remain explicit |
| GET /v1/update | Check GitHub's latest release for portable installs. Windows packages return `channel: "windows-package"`, `available: false`, the current `version`, the Store updates `url` and `asset: null` without querying GitHub. |
| POST /v1/maintenance | `{enabled:true}` atomically rejects new jobs only if all current work has finished; updater releases the gate on preparation errors |

Events: `{id,job,agent,kind,text,stage,time,folder,data}`. Kinds include `workflow`, `phase`, `note`, `tool`, `message`, `usage`, `limits`, `done`, `error`. Additive `workflow` events announce a real round with `stage` and `data.participants`, for example `review` with `["codex","grok"]`. Count each member's latest `phase` (`Done` or `Failed`) in that stage; do not infer progress from text volume or elapsed time. Stages are work, review, optional refinement/verification, discussion and report. A `question` workflow stage means the lead requested clarification; the job completes its turn and the user's next message continues from history. Consumers should tolerate unknown event kinds. Streamed notes are bounded and paced; final reports are retained separately. Events are stored before broadcast. Consumers deduplicate by ID. Jobs left running after an engine restart become `interrupted`; no claim of transparent CLI process resumption is made. Work can be continued with a new message using the saved transcript.

The optional lead executes changes requested by the user. Optional reviewers inspect and offer opinions. Confirmed findings on implemented changes trigger one bounded correction pass, followed by read-only rechecks. Participants compare findings in a conference. The final report distinguishes actual changes from recommendations and attributes opinions. Starting in runtime revision 12, new council reports begin with engine-generated participation counts from the accepted job's team and initial outcomes. An individual review response counts once, independent of any later recheck or conference outcome. Standard/coder-only/all-agent permissions preserve the v2 policy. With all-agent bypass the review-only role is a prompt instruction, not enforced filesystem isolation.

For explicit short-answer requests, runtime revision 13 can include `report_summary` in a council message. It is a prefix of `text`, which retains the full Markdown report. Clients can display the prefix and let readers expand the remainder. Older messages omit the field.

The desktop changes route returns `{available,source?,skipped,files:[{path,kind,patch,truncated}]}`, or `null` for older and unfinished jobs without a record. Git capture (`source: "git"`) uses tracked and non-ignored untracked files. A project outside Git (`source: "folder"`, added in revision 13) compares supported source, documentation and configuration files and skips hidden entries, common generated folders, and nested repositories. Nested reference folders and known private locations are excluded. These compare bytes during the job, so concurrent external edits may appear. The Git index and refs are untouched. Oversized files, traversal or capture limits and inaccessible inputs can limit or prevent capture. Review prompts can receive a bounded excerpt. The full saved comparison is omitted from companion responses and events.

Parallel rounds persist completed messages immediately, without waiting for slower peers; the next round still waits for the required current results. Evidence and preferred report-agent ordering remain deterministic. Failed initial reviewers are excluded from verification, failed verifiers are excluded from discussion, and failed discussants are excluded from report selection. Retained results provide a clearly labelled fallback if no participant can synthesize them. A lead `QUESTION` response returns directly for user input instead of spending more calls on review/discussion.

`state.activity` is a compact snapshot: the latest complete note per agent plus up to 40 events of each workflow/phase/tool/error/done kind. Full reports are in `messages`; full original event history is retained for SSE replay. Clients merge newer streamed events by ID rather than overwriting them with an older in-flight snapshot. Milestone events must survive client compaction even when tools produce many updates.

Desktop `settings.agent_profiles` (previously `claude_profiles`, still accepted as input) holds `{name,config_dir,display_name?}` entries. `name` is a stable participant ID selected by `coder` or `reviewers`. A display name change updates `state.agent_labels` and preserves that ID. The configuration folder must be an existing absolute directory when added and distinct from the other profile folders and the provider defaults. Account usage is refreshed against the selected profile's local sign-in. A Claude profile without local OAuth data can still supply quota windows through CLI events. Companion snapshots return display names for the paired team and omit profile paths. A work grant needs a new pairing if a selected profile's directory mapping changes.

The desktop-only `GET /v1/{provider}/accounts` (provider is `claude` or `codex`) checks the default login, registered folders and discovered candidates. `POST /v1/{provider}/accounts/check` checks an explicitly selected folder from `{config_dir}`. The response includes authentication status and, when reported for a signed-in Claude.ai session, `account_email`. The response is marked `no-store` and the reported email is absent from saved settings, project history and companion responses. `POST /v1/{provider}/accounts/prepare` creates a private account folder and returns a sign-in command with its `login_shell` for the host OS. Reusing the optional UUID `request_id` returns the same folder after a lost response or runtime restart. Saving the team through `PUT /v1/settings` connects the selected profile.

`limits[agent]` contains sanitized `{status,windows,source,updated_at,message}` with optional `auth_source` and `refreshing`. Windows contain `{label,used,reset}` where `used` is a percentage from 0–100 and `reset` is epoch seconds or null. Status distinguishes `ok`, `loading`, `signed_out`, `unavailable`, `error`, `stale` and `unlimited`. Failed refreshes preserve prior valid windows as `stale`, retaining their successful `updated_at` and recording an `attempted_at`. Partial CLI events merge windows instead of removing other known periods. Missing data is not zero usage. Project token totals in `usage` are independent of account limits. Account probes reuse local sign-ins without returning credentials. Global limit events have an empty job ID and apply across project selections. File previews canonicalize paths against the selected project and reference roots; binary files are rejected and rendering is capped at 512 KiB / 3,000 lines.

The local Vite development server exposes a same-origin-only `GET /__council/runtime` bridge on 127.0.0.1:1420. It starts or connects to the same Rust engine, never a mock backend. Runtime descriptors include a compatibility revision; an incompatible engine is replaced only when no work is running.

Existing settings and chat JSON files are read and imported once; original files remain available. All new runtime state is stored in SQLite. Windows CLI children run under the signed-in user's account, not LocalSystem.
